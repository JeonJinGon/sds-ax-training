# Day 6. Supervisor 인시던트 대응팀

[← 전체 미션 맵](../README.md)  ·  [← Day 5](../day05/README.md)  ·  [Day 7 →](../day07/README.md)

장애가 나면 다들 한 사람을 찾았습니다. 로그를 어디부터 열어야 하는지, 지표 대시보드에서 어느 패널이 진짜인지, 인증서가 만료되면 누구에게 전화하는지 — 그게 전부 그 사람 머리에만 있었기 때문입니다.

문제는 그 사람이 하나라는 것. 로그를 읽는 20분 동안 지표는 아무도 보지 않았습니다. 런북을 뒤지는 사이 로그 창은 그대로 멈춰 있었다. 휴가라도 가면 그 주에 난 장애는 전부 처음 겪는 일.

오늘 만드는 건 그 머릿속을 셋으로 쪼갠 팀. 로그만 보는 Agent, 지표만 보는 Agent, 런북만 뒤지는 Agent, 그리고 질문을 읽고 누구를 부를지 정하는 Supervisor. Day2에서 만든 검색과 Day4에서 만든 도구가 여기서 한 시스템으로 합쳐집니다.

쪼개는 순간 없던 비용이 생기죠. Agent가 셋이면 호출도 셋, 누구를 부를지 정하는 판단 자체도 비용. 그래서 오늘 채점의 절반은 "얼마나 좁게 나눴는가"에 걸려 있습니다.

## 학습 목표

- Supervisor가 질문을 읽고 목적지를 고르는 구조. 고르는 근거를 규칙으로 먼저 써 보면 무엇을 보고 나누는지가 드러납니다.
- 전문 Agent는 담당 범위와 도구, 프롬프트를 좁게 잡을 것.
- Agent를 늘린 만큼 호출 수와 추적 비용도 같이 늘어난다는 것. 어디까지 늘릴지 오늘 직접 재 볼 것.
- 워커가 내놓은 답을 그대로 내보내지 않고 한 번 거르기. (심화)

## 기초 파트 (7점)

### 구현할 것

```python
AGENT_NAMES: list[str]                 # 전문 Agent 3개
AGENT_TOOLS: dict[str, list[str]]      # Agent -> 도구 목록
route_question(question) -> list[str]  # 어느 Agent로 보낼지 (LLM 없이)
build_supervisor(llm=None)             # 컴파일된 그래프
```

### 요구사항

1. 전문 Agent는 셋. `log_agent`, `metric_agent`, `runbook_agent`. 이 이름이 그대로 그래프 노드로 존재해야 한다.

   이름이 곧 담당 범위의 선언이고, 답이 이상할 때 어느 프롬프트를 열어야 하는지 알려 주는 표지판. 한 덩어리 Agent가 로그도 보고 지표도 보면 오답 하나에 고칠 자리가 특정되지 않습니다. 프롬프트 전체를 다시 쓰는 수밖에 없다.

2. 도구를 격리하세요. 같은 도구가 두 Agent에 걸쳐 있으면 안 됩니다. 도메인 기준으로 나눌 것.

   "혹시 몰라서" 얹어 두면 Supervisor가 어디로 보낼지 헷갈립니다. 더 비싼 건 그다음. 같은 질문이 어제는 `log_agent`로, 오늘은 `metric_agent`로 갑니다. 두 답이 서로 다를 때 어느 쪽이 맞는지 가릴 근거가 사라진다. 격리는 성능이 아니라 재현을 위한 것.

3. `route_question`은 LLM을 부르지 않고 결정적 규칙으로 배분합니다.

   - `log_agent`: 로그, 에러, 예외, 스택, 트레이스, 5xx/500, 영문 `log`·`exception`·`trace`
   - `metric_agent`: 지표, 수치, 지연, 레이턴시, CPU, 메모리, 오류율, 배포, 영문 `metric`·`latency`
   - `runbook_agent`: 절차, 대응, 방법, 런북, 매뉴얼, 담당, 누구, 어떻게, 영문 `runbook`

   여러 주제가 섞이면 해당하는 Agent를 모두, 어디에도 걸리지 않으면 빈 목록. 채점은 위 목록에 없는 동의어와 영문 표기로도 확인하니, 단어를 그대로 베끼지 말고 같은 뜻의 표현을 함께 넣어 둘 것.

   배분까지 모델에게 맡기면 오답이 났을 때 워커가 틀렸는지 배분이 틀렸는지 가릴 수 없습니다. 확률이 두 겹으로 쌓인다. 이 층만 코드로 못 박아 두면 최소한 "어느 Agent로 갔는가"는 언제 물어도 같은 답.

   그리고 해당하는 Agent만 반환할 것. 전부 부르면 정확도는 오르지만 호출 비용이 폭증합니다. 질문 하나에 Agent 셋이면 토큰도 세 배, 응답은 가장 느린 쪽을 기다리는 시간. 질문이 몰리는 시간대에는 그 차이가 그대로 대기열로 쌓인다.

4. `routing_test.json` (day06 폴더)에 6문항 이상, 단일 Agent 3문항 이상, 복합 1문항 이상. 각 문항에 `question`과 `expected`를 넣고 `expected`는 Agent 이름의 리스트로 둘 것.

   라우팅 규칙은 단어를 하나 넣을 때마다 조용히 넓어져서, `배포`를 `metric_agent` 쪽에 넣는 순간 "배포 절차가 어떻게 되나요"가 런북 대신 지표로 갑니다. 오늘 손본 규칙이 어제 맞히던 질문을 깨뜨렸는지 알려 줄 수 있는 건 본인이 미리 적어 둔 문항뿐. 복합 문항을 굳이 요구하는 이유도 같아요. 하나만 고르는 구현은 둘을 골라야 하는 질문에서 조용히 하나를 버리는데, 단일 문항만 모아 두면 그게 끝까지 보이지 않죠.

5. `eval_set.json` (저장소 루트)에 `routing` 유형을 2문항 이상 추가합니다 (`d6-01`, `d6-02`).
   Day2부터 누적해 Day7에 12문항 이상, 5유형 이상이 되어야 합니다.

   ```json
   [{"question": "payment-api 로그에 어떤 에러가 찍혔나요?", "expected": ["log_agent"]}]
   ```

   이 두 문항은 오늘 채점표에 없어요. 그럼 왜 지금 쓸까요? 내일 Day7에서 누적 12문항을 셀 때 이 둘이 그 안에 들어간다. 지금 건너뛰고 마지막 날 몰아서 채우면, 그때 시스템이 이미 잘하는 것만 묻는 문항이 만들어집니다. 평가셋이 후하게 나오는 가장 흔한 경로.

### 채점 기준 (기초 7점)

| 배점 | 항목 | 검사 지점 |
|---|---|---|
| 2점 | **구성** | `AGENT_NAMES` 3개 이상, 이름 중복 없음. 컴파일된 그래프 노드에 그 이름이 모두 있음 |
| 2점 | **도구 격리** | `AGENT_TOOLS`의 키가 `AGENT_NAMES`와 같고 Agent마다 도구가 있으며, 같은 도구가 두 곳에 없음 |
| 1점 | **라우팅 정확도** | 공개 케이스에서 필요한 Agent를 정확히 고름 |
| 1점 | **라우팅 테스트셋** | 6문항 이상, 단일 3+ / 복합 1+ |
| 1점 | **확장 검사 게이트** | 10개 중 8개 이상 |

라우팅 공개 케이스는 다섯 개. 로그 질문, 지표 질문, 런북 질문, 로그와 지표가 섞인 복합 질문, 그리고 "오늘 점심 메뉴 추천해줘". 한 건까지는 틀려도 통과, 두 건이면 그 자리에서 실패.

확장 검사 공개분도 여섯 개. 빈 질문에 빈 목록 / 무관한 질문에 빈 목록 / `로그`가 500번 반복된 질문에도 리스트 반환 / 반환 타입이 리스트 / 같은 Agent가 결과에 두 번 들어가지 않음 / "지표만 알려주세요"에 Agent 두 개 이하. 다섯 개를 못 넘기면 실패고 나머지 넷은 채점 때 붙는 몫. 채널에 올라오는 질문은 대개 지저분한데, 라우터가 거기서 예외를 던지면 뒤에 붙은 Agent 셋은 실행조차 못 합니다.

## 심화 파트 (3점)

### 왜 필요한가

워커는 아무것도 못 찾았을 때도 문장은 만들어 냅니다. "확인함" 같은 세 글자, 또는 근거 하나 없이 확실하다고 말하는 한 문단. 인시던트 채널에서는 이 둘이 제일 비싸죠. 대응하던 사람이 그 문장을 읽고 다음 조치를 정한다. 그럼 검사는 어디에 붙여야 할까요? 워커마다 붙이면 같은 코드를 셋에 세 번 짜야 합니다. 그중 하나를 고치면 나머지 둘은 잊게 되죠. 그래서 게이트는 Supervisor 한 곳.

### 구현할 것

```python
judge_output(agent_name, output) -> {"keep": bool, "reason": str}
```

그리고 워커 노드가 이 판정을 거치도록 연결합니다.

### 요구사항

1. 판정 규칙 셋. `judge_output`도 LLM을 호출하지 않습니다.

   - 내용이 비었거나 20자 미만이면 `keep=False`, 사유는 "저가치"
   - 근거 없는 단정("확실합니다" 등)인데 수치나 출처가 없으면 `keep=False`, 사유는 "근거 없는 단정"
   - 그 외에는 `keep=True`

   두 번째 규칙이 왜 따로 있을까요? 길이만 재면 근거 하나 없이 "확실합니다"와 "틀림없습니다"로만 채운 답이 20자를 넘겨 그대로 나갑니다. 반대로 `NullPointerException이 1243건`처럼 수치가 박힌 단정까지 막으면 쓸 만한 답이 사라진다. 단정 표현과 근거 유무를 함께 봐야 하는 자리.

   사유를 남기는 것도 채점 항목입니다. 억제만 하고 이유가 없으면 다음 날 남는 건 "답이 안 나왔다" 한 줄뿐. 게이트가 과하게 잠긴 건지 워커가 부실한 건지 구분할 방법이 없습니다.

2. 연결: 워커 노드가 이 판정을 실제로 거칠 것.

### 채점 기준 (심화 3점)

| 배점 | 항목 | 검사 지점 |
|---|---|---|
| 1점 | **게이팅 결정성** | 정상, 빈 값, 짧은 값, 근거 없는 단정 네 상황을 구분 |
| 1점 | **저가치 억제** | 억제할 때 사유가 붙음 |
| 1점 | **파이프라인 연결** | Supervisor 실행 결과에 게이팅이 반영됨 |
