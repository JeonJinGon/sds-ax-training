# Day 1. 운영 알람 트리아지 체인

[← 전체 미션 맵](../README.md)  ·  [Day 2 →](../day02/README.md)

> 모니터링 알람 하나를 티켓에 적재할 분류 결과로 바꾸고, 담당팀에 보낼 안내 초안까지 한 번에 뽑습니다.

## 학습 목표

- 모델에게 형식을 강제하는 법. 프롬프트에 "JSON으로 답해"라고 적어 두면 지킬 때도 있고 안 지킬 때도 있습니다. 스키마와 파서로 묶어 두면 어긴 출력이 파서에서 걸립니다.
- LCEL로 프롬프트·모델·파서를 조립하기. 두 갈래를 한 번에 돌리는 `RunnableParallel`까지 써 볼 것.
- LLM의 판단 위에 결정적 규칙을 얹는 하이브리드 구조. (심화)

## 시나리오

당직 첫날 새벽 3시 14분. 휴대폰에 뜬 알람은 이게 전부.

```json
{
  "alert_id": "ALT-2026-0811-0042",
  "service": "payment-api",
  "raised_at": "2026-08-11T03:14:22+09:00",
  "message": "HTTP 5xx ratio 12.4% over 5m (threshold 1%)",
  "region": "ap-northeast-2"
}
```

여기서 30초 안에 정할 것 셋. 얼마나 급한가, 어느 팀을 깨우는가, 무엇부터 열어 보는가?

옆자리 선배는 커피 내리는 동안 이걸 끝내죠. 첫 당직이면 `payment-api`가 무슨 서비스인지부터 찾게 됩니다. 그동안 5xx 비율은 임계치의 열두 배에서 더 올라가는 중. 오늘 만드는 건 그 30초를 대신할 체인.

## 기초 파트 (7점)

### 무엇을 만드나

알람 dict 하나가 들어가면 결과 두 개가 동시에 나오는 체인. `triage`는 구조화된 dict로, 티켓 시스템에 그대로 적재할 값. `notice`는 담당팀 채널에 붙여넣을 안내 초안 문장. 기계가 읽을 것과 사람이 읽을 것을 한 덩어리로 뭉쳐 놓으면 양쪽 다 어정쩡해집니다. 갈래를 나눠 둘 것.

### 구현할 것

`practice/starter/submission.py`의 TODO를 채웁니다. **이름과 시그니처는 바꾸지 마세요.** 채점기가 이 이름으로 함수를 찾습니다.

```python
TRIAGE_SCHEMA                      # 분류 결과 Pydantic 스키마
build_triage_chain(llm=None)       # 알람 -> 구조화 dict
build_notice_chain(llm=None)       # 알람 -> 안내 초안 문자열
build_full_chain(llm=None)         # 위 둘을 병렬로 묶어 dict 반환
```

### 요구사항

1. `TRIAGE_SCHEMA`: `BaseModel`을 상속하고 필드 4개 이상을 둡니다. 모든 필드에 `description`을 달 것.
   `severity`는 `Literal` 또는 `Enum`으로 정해진 값 중 하나만 받게 할 것.

   모델이 읽는 것은 필드 이름과 이 설명문뿐. 기준을 안 적어 두면 모델은 무엇을 근거로 P1과 P2를 가를까요? 알아서 상상한 기준으로 등급을 매기고 그 대가는 새벽 3시에 엉뚱한 팀을 깨우는 호출. 등급을 자유 문자열로 열어 두는 것도 마찬가지. `높음`과 `critical`과 `P1`이 한 컬럼에 섞이면 그 컬럼을 보고 티켓을 넘기던 라우팅 규칙이 먼저 무너집니다.

2. `build_triage_chain`: `prompt | llm | parser` 형태로 조립하고 파서의 `format_instructions`를 프롬프트에 실제로 주입합니다.

   스키마를 정의만 하고 프롬프트에 넣지 않으면 모델은 그런 계약이 있는 줄도 모릅니다. 파서 쪽만 엄격해진 상태라 실패율은 되레 올라가죠. 형식 지침이 계약서를 모델에게 보여 주는 유일한 통로.

3. `build_notice_chain`: system 메시지로 역할을 지정합니다. 교안 예시 문구는 지우고 본인 조직의 말투와 맥락으로 다시 쓸 것.

   이 초안은 사람이 읽고 그대로 채널에 붙여넣는 문장. 호출 절차도 존댓말 수위도 팀마다 다르죠. 기본 문구를 그냥 두면 결국 아무도 안 쓰고 매번 손으로 고쳐 쓰게 되죠. 그러면 체인을 만든 이유가 없습니다.

4. `build_full_chain`: `RunnableParallel`로 두 체인을 묶어 `{"triage": ..., "notice": ...}` 형태로 반환합니다.

   순서대로 이어 붙이면 모델 왕복 두 번이 그대로 더해지지만 병렬이면 느린 쪽 하나만 기다리면 됩니다. 알람이 분 단위로 몰리는 시간대에 그 차이가 대기열로 쌓여요.

### 채점 기준 (기초 7점)

| 배점 | 항목 | 통과 조건 |
|---|---|---|
| 2점 | **스키마 계약** | `TRIAGE_SCHEMA`가 `BaseModel` 서브클래스이고 필드 4개 이상. 모든 필드에 `description`이 있고, `severity`가 열거형으로 제한됨 |
| 2점 | **병렬 조립** | `build_full_chain` 결과가 `triage`·`notice` 두 키를 가진 dict이고, 두 갈래가 각각 채워짐 |
| 1점 | **형식 지침 주입** | 분류 체인이 모델에게 보낸 프롬프트에 파서의 `format_instructions` 내용이 실제로 들어 있음 |
| 1점 | **역할 지정** | 안내 체인에 system 메시지가 있고 30자 이상이며 starter 기본 문구와 다름 |
| 1점 | **확장 검사 게이트** | 아래 10개 중 8개 이상 통과 |

확장 검사 10개는 알람 모양이 흔들려도 파이프라인이 버티는지 봅니다.

`message`가 빈 문자열 / `service` 키 누락 / 본문이 4000자로 긴 알람 / 한글·영문 혼재 / 특수문자와 이모지 / `raised_at`이 잘못된 형식 / 숫자만 있는 메시지 / 중첩 dict가 섞인 알람 / 알람 2건 연속 처리 / 같은 알람 재처리 시 동일 구조 반환

`scripts/grade.py`로 로컬에서 도는 공개분은 이 중 여섯 개, 다섯 개를 못 넘기면 그 자리에서 실패. 나머지는 채점 때 붙는 몫. 모니터링 룰을 하나 추가하거나 도구를 바꿀 때마다 알람 모양은 조금씩 흔들리는데, 필드 하나 비었다고 새벽 파이프라인이 멈추면 곤란합니다.

## 심화 파트 (3점)

통과선은 7점. 심화를 못 해도 과제는 통과. 대신 해내면 대시보드에 심화 달성으로 기록되고 Mini PJT에서 이 코드를 그대로 씁니다.

### 왜 필요한가

LLM은 형식을 잘 지키다가도 어느 순간 깨뜨립니다. 그리고 `payment-api`가 죽었다면 모델이 뭐라고 분류했든 최우선. 조직이 이미 답을 정해 둔 판단을 매번 모델에게 다시 물을 이유는 없죠. LLM이 매긴 등급을 받아 온 다음, 정해 둔 규칙으로 한 번 더 덮어씁니다.

### 구현할 것

```python
apply_severity_rules(triage: dict, alert: dict) -> dict
```

그리고 `build_full_chain`이 이 함수를 파이프라인 안에서 호출하도록 연결할 것.

### 요구사항

1. 깨진 출력 복구: 모델이 JSON이 아닌 것을 뱉어도 `build_full_chain`은 예외를 던지지 않고 dict를 반환할 것.
   복구된 결과에는 그 사실을 알 수 있는 표시를 남깁니다 (예: `severity`를 가장 높은 값으로 두거나 `parse_failed` 같은 표시).

   파서 예외 하나로 파이프라인이 서면 그 알람은 어디에도 도착하지 않아요. 아무도 모르는 채로. 표시를 남겨 두면 다음 날 아침에 "이 값은 모델이 아니라 복구 경로가 만든 것"을 구분할 수 있고 복구가 몇 건이었는지도 셀 수 있습니다.

   힌트: `try/except`로 감싸 기본값을 돌려줘도 되고, `OutputFixingParser`나 재시도를 붙여도 되고요. 방법은 자유.

2. 결정적 규칙 오버라이드: `apply_severity_rules`는 LLM을 호출하지 않고 아래 규칙을 적용합니다.

   - `service`가 중요 서비스 목록에 있으면 severity를 최소 `P2`로 올림. 이미 더 높으면 유지
   - `message`에 `5xx` 또는 `outage`가 포함되면 최소 `P1`로 올림
   - 위 둘 다 해당하면 더 높은 쪽을 적용
   - 아무 조건도 해당 없으면 모델 판단을 그대로 둠

   중요 서비스 목록은 모듈 상수로 두고 최소 3개 이상 넣습니다. 규칙이 적용됐다면 그 사실을 결과에 남길 것 (예: `rule_applied` 키).

   여기가 조직의 판단이 들어가는 자리다. 어떤 서비스가 멈추면 새벽에도 사람을 깨우는지 모델은 알 수 없고 알 필요도 없습니다. 그 목록이 곧 다음 당직자가 코드 대신 읽을 우선순위 정책. 적용 흔적까지 남겨야 나중에 "이 등급은 모델이 매긴 건가, 규칙이 올린 건가"를 되짚을 수 있습니다.

3. 연결: `build_full_chain`의 `triage` 결과가 규칙 적용을 거친 값일 것.

### 채점 기준 (심화 3점)

| 배점 | 항목 | 통과 조건 |
|---|---|---|
| 1점 | **깨진 출력 복구** | 모델이 `"죄송합니다, 알 수 없습니다"`처럼 JSON이 아닌 응답을 해도 예외 없이 dict 반환. 복구 표시 존재 |
| 1점 | **규칙의 결정성** | `apply_severity_rules`를 LLM 없이 직접 호출했을 때, 4가지 조건 조합에서 규칙대로 동작. 상수 반환이면 실패 |
| 1점 | **파이프라인 연결** | `build_full_chain` 결과의 `triage`에 규칙 적용 흔적이 남아 있음 |
