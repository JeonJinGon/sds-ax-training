# Day 4. 운영 지원 MCP 서버와 장애 복구

[← 전체 미션 맵](../README.md)  ·  [← Day 3](../day03/README.md)  ·  [Day 5 →](../day05/README.md)

어제 만든 조사 Agent가 자산 상태를 물어보다 남긴 로그. 뒤에서 여덟 줄만 잘라 왔습니다.

```text
10:22:41  agent  tool_call get_asset_status(asset_id="SRV-002")
10:22:41  http   GET /assets/SRV-002  Authorization: Bearer sk-internal-dummy-1234
10:22:46  http   ValueError: schema validation failed: field 'status' missing
10:22:51  http   retry 1 ...   ValueError: schema validation failed: field 'status' missing
10:22:56  http   retry 2 ...   ValueError: schema validation failed: field 'status' missing
10:26:12  http   retry 39 ...  ValueError: schema validation failed: field 'status' missing
10:26:17  agent  Traceback (most recent call last): ... ValueError: schema validation failed
10:26:17  agent  session aborted
```

`status` 필드가 빠진 응답 하나를 서른아홉 번 더 물었습니다. 마흔 번째에도 그 필드는 안 생기죠. 그 사이에 4분과 API 호출 한도가 나갔습니다.

두 번째 줄에는 토큰이 통째로 찍혔죠. starter에 있는 `BACKEND_TOKEN` 값 그대로. 이 줄을 로그 수집기가 어디까지 실어 갔는지 아는 사람은 아직 없습니다.

제일 비싼 건 마지막 두 줄. 예외가 도구 밖으로 나가는 순간 Agent 세션이 통째로 끝났습니다. 조사는 거기서 중단. 담당자는 결국 콘솔을 직접 열었고 어제 붙인 순환 그래프는 한 바퀴도 못 돌았습니다.

오늘 만드는 건 저 로그가 다르게 찍히게 하는 층. 도구는 예외 대신 문장을 돌려주고, 실패는 종류별로 갈라지고, 답이 어느 경로에서 나왔는지 반환값에 남는 구조. 그 도구들을 MCP로 내보내는 것까지가 오늘 몫.

## 학습 목표

- 모델이 도구를 고를 때 보는 건 이름과 설명, 인자 스키마. MCP로 내보내는 순간 그 설명문은 우리 코드 밖에서 읽히죠.
- 에러 메시지가 모델에게는 프롬프트로 쓰인다는 것. 문장 하나로 다음 호출이 달라진다.
- MCP가 M×N을 M+N으로 바꾸는 원리. 서버를 직접 띄워 볼 것.
- 실패 종류마다 대응이 갈리는 지점. (심화)

## 기초 파트 (7점)

### 구현할 것

`practice/starter/submission.py`의 TODO를 채웁니다. 이름과 시그니처는 손대지 말 것.

```python
TOOL_SPECS                                   # MCP로 노출할 도구 명세 3개
TOOLS_IMPL                                   # 이름 -> 실제 함수
get_asset_status(asset_id, fetch=None)       # 재시도 + 대체 경로
get_asset_status_backup(asset_id)            # 대체 조회 경로
```

여기에 더해 `day04/mcp_server.py`에 `fastmcp` 서버를 만들고 위 도구를 노출할 것.

Day 6 Supervisor가 쓸 도구 목록이 오늘 만든 것으로 채워지니, 설명문을 대충 적어 두면 이틀 뒤에 그 문장을 그대로 다시 보게 되죠.

### 요구사항

1. 도구 3개: `search_runbook`, `get_service_owner`, `query_recent_incidents`

   `TOOL_SPECS`의 각 항목은 이렇게 생겼습니다.

   ```python
   {
     "name": "search_runbook",
     "description": "증상 키워드로 대응 런북을 찾습니다. ...",   # 30자 이상
     "args": {"symptom": "증상 키워드. 예: 5xx, oom, cert"},     # 인자마다 설명
   }
   ```

   `TOOLS_IMPL`은 `{"search_runbook": search_runbook, ...}` 형태. 각 함수는 문자열을 반환할 것.
   정상 조회 결과에는 `practice/data/ops_assets.json`에서 읽은 값이 실제로 담길 것.
   없는 값을 넣었을 때도 예외를 던지지 말고, 무엇이 잘못됐는지 알려 주는 문자열을 돌려줄 것.

   어제까지는 이 설명문을 우리가 만든 Agent가 읽었습니다. MCP로 내보내면 읽는 쪽이 바뀌죠. 다른 팀 클라이언트, 다른 모델, 우리가 프롬프트를 손댈 수 없는 세션. 거기서 도구를 잘못 골라도 우리 로그에는 무엇이 남을까요? 아무것도 남지 않습니다. `args`의 인자 설명이 특히 그런 자리인데, 여기가 비면 모델이 인자 이름을 지어내고 그 호출은 우리 함수에 닿기도 전에 깨집니다.

   예외 대신 문자열을 돌려주라는 요구는 위 로그의 마지막 두 줄과 같은 이야기. "등록되지 않은 증상 키워드예요. 쓸 수 있는 값: 5xx, oom, cert" 한 줄을 받으면 모델은 다음 호출을 고쳐 잡습니다. 예외를 받으면 고칠 기회도 없이 루프가 서죠.

2. `get_asset_status(asset_id, fetch=None)`에서 `fetch`는 외부 백엔드를 부르는 함수입니다.
   - `fetch`가 없으면 기본 조회로.
   - `fetch`가 실패하면 재시도. 그래도 안 되면 `get_asset_status_backup`으로 넘어갈 것.
   - 재시도가 성공하면 그 응답 내용을 반환 문자열에 담으세요. 되살아난 값을 버리고 폴백 문구만 돌려주면 안 됩니다.
   - **어떤 경우에도 예외를 밖으로 던지지 않습니다.** 상황을 설명하는 문자열을 대신 반환하세요.
   - 대체 경로로 넘어갔다면 반환 문자열에 `get_asset_status_backup`이라는 이름을 남기세요.
     모델이 그다음에 무엇을 할지 고르려면 이 이름이 필요하니까요.

   이름을 남기라는 건 모델만을 위한 요구가 아닙니다. 캐시된 값을 지금 상태로 착각한 담당자가 "정상입니다"를 그대로 보고에 옮기는 일이 실제로 생기니까요. 사후에도 마찬가지. 정상 경로와 폴백이 구분되지 않으면 폴백 비율부터 셀 수가 없고, 백엔드가 반나절 죽어 있어도 대시보드는 조용합니다.

3. 로그에 자격증명을 남기지 말 것. 키나 토큰 문자열이 반환값이나 로그에 그대로 들어가면 안 됩니다.

   반환 문자열이 가는 곳은 로그만이 아닙니다. 모델 컨텍스트에도 들어가고, 트레이스에도 적재되고, Day 7의 평가 기록까지 같이 따라갑니다. 한 번 새면 회수할 자리가 그만큼 늘어난다는 뜻. 위 로그 두 번째 줄 한 줄에 토큰 교체와 영향 범위 조사로 하루가 갑니다.

4. `eval_set.json`에 문항을 추가합니다 (저장소 루트). `tool_recovery` 유형으로 2문항 이상 쓸 것.
   도구가 실패했을 때 복구했는지를 묻는 질문. id는 `d4-01` 형식으로 이어 붙일 것.

   복구 경로는 평소에 한 번도 안 도는 코드다. 백엔드가 멀쩡한 날엔 실행조차 안 되니 조용히 망가져도 티가 안 나는데, 이 코드가 필요한 날은 정확히 백엔드가 죽은 날. 문항으로 박아 두면 Day 7에서 유형별 통과율에 잡힙니다.

| 배점 | 항목 | 검사 내용 |

| 2점 | **도구 명세** | 3개, 설명 30자 이상, 인자마다 설명, `TOOLS_IMPL`과 이름이 일치 |
| 2점 | **호출 동작** | 정상 인자는 기대 값을, 없는 값은 예외 대신 안내 문자열을 반환 |
| 1점 | **장애 복구** | `fetch`가 계속 실패해도 예외 없이 문자열 반환 + 대체 도구 이름 명시 |

## 심화 파트 (3점)

### 왜 필요한가

실패하면 일단 재시도부터 거는 코드가 많죠. 맨 위 로그가 그 코드가 남긴 흔적. 스키마가 어긋난 응답은 백 번을 다시 물어도 같은 모양으로 오면서 시간과 API 예산만 씁니다. 재시도를 걸기 전에 어떤 실패인지부터 가를 것.

### 구현할 것

```python
classify_failure(error) -> str    # "retryable" | "backoff" | "fatal"
```

이 분류 결과에 따라 `get_asset_status`의 동작이 갈리도록 연결할 것.

### 요구사항

1. 세 갈래로 나눕니다.

   - `retryable`: 타임아웃, 일시적 연결 오류. 짧게 재시도.
   - `backoff`: 요청 한도 초과 (rate limit). 간격을 늘려 재시도.
   - `fatal`: 스키마 오류, 인증 실패, 없는 자원. 재시도하지 않고 즉시 대체 경로.

   가르는 기준은 하나. 다시 물었을 때 답이 달라질 수 있는가? 타임아웃은 달라질 수 있고, 스키마 오류는 몇 번을 물어도 그대로인데, 한도 초과는 달라지긴 하지만 같은 속도로 두드리면 한도만 더 깎아 먹습니다. 셋을 한 덩어리로 다루면 그중 둘에서는 반드시 손해를 봅니다.

2. `get_asset_status`가 이 판정에 따라 갈릴 것. 재시도 상한은 starter의 `MAX_RETRIES`.

   타임아웃에서는 백엔드를 2회 이상 부르되 `MAX_RETRIES` 안에서 멈추고 스키마 오류에서는 1회를 넘기지 않을 것. 상한이 없으면 위 로그의 39회가 그대로 재현되죠. 하한이 없으면 한 번 튄 네트워크에도 폴백으로 떨어져 캐시 값이 답이 됩니다.

### 채점 기준 (심화 3점)

| 배점 | 항목 | 검사 내용 |
|---|---|---|
| 1점 | **분류의 결정성** | 6가지 오류 상황에서 세 갈래대로 분류. 상수 반환이면 실패 |
| 1점 | **fatal 즉시 폴백** | 스키마 오류에서 재시도 횟수가 1회 이하 |
| 1점 | **retryable은 재시도** | 타임아웃에서는 2회 이상 재시도하고, 총 호출은 상한 이하 |
