# Day 7. 계측과 누적 평가

[← 전체 미션 맵](../README.md)  ·  [← Day 6](../day06/README.md)  ·  [Day 8~10 →](../day08/README.md)

닷새 전 Day2에서 `eval_set.json`을 만들며 문항 몇 개를 심어 뒀습니다. 그중 하나는 그때 확실히 빨간불이었을 것. 런북에 없는 것을 물어보는 `no_answer` 문항 같은 것. 검색은 엉뚱한 문서를 물어 왔고, 모델은 그 문서로 그럴듯한 답을 지어냈습니다.

오늘 할 일은 그 문항을 회수하는 것. 그 사이에 검색 앞에는 게이트가 붙었다. 도구와 순환이 생겼고, 위험한 요청을 막는 층이 섰고, 질문을 나눠 보내는 Supervisor까지 붙었습니다. 그래서 지금은 통과하나요?

"좋아진 것 같다"로는 아무것도 결정할 수 없습니다. 통과했다면 무엇이 그걸 바꿨는지, 아직 실패한다면 어디서 막히는지. 오늘 만드는 건 그 질문에 매번 같은 방식으로 답하는 장치.

평가셋을 마지막 날 몰아서 만들면 안 되는 이유가 여기 있습니다. 지금 시스템을 보면서 문항을 쓰면 손은 자연히 지금 잘 되는 쪽으로 간다. 실패하던 문항은 이미 고쳐졌거나 기억에서 지워졌고요. 그렇게 만든 평가셋은 통과율이 높게 나오는데 그 숫자로 내릴 수 있는 판단은 없습니다. 닷새 전의 실패가 남아 있어야 오늘의 통과가 뜻을 갖는 것. 재는 대상은 시스템이 아니라 변화입니다.

## 학습 목표

- 관측은 무엇을 했는지를 남기고, 평가는 잘했는지를 판정하는 일. 둘은 다른 층이에요.
- trace는 결정적 구조체. 모델이 무슨 말을 했든 이벤트 개수와 필드는 확정 검사할 수 있습니다.
- 통과율 하나로는 품질이 안 보여요. 유형별로 쪼개야 뚫린 곳이 드러나죠.
- 한쪽을 고쳤을 때 다른 쪽이 깨지지 않았는지 확인하기. (심화)

## 기초 파트 (7점)

### 구현할 것

```python
TraceCollector                              # 실행 기록
run_eval(answer_fn, eval_set, judge=None)   # 유형별 집계
```

### 요구사항

1. `TraceCollector`: `record(event, name, **fields)` / `events` / `dump(path)`
   - `event`는 `llm_start`, `llm_end`, `tool_start`, `tool_end` 중 하나입니다
   - `dump`는 JSON Lines로 씁니다. 한 줄에 이벤트 하나.
   - 지연 시간 같은 부가 필드도 실을 수 있어야 합니다

   답이 이상할 때 물어볼 건 둘입니다. 모델이 이상한 말을 했나, 도구가 이상한 값을 줬나. trace가 없으면 그 둘이 갈라지지 않고, 결국 프롬프트만 계속 만지게 됩니다. 한 줄에 이벤트 하나라는 형식도 취향이 아니라 조건. 실행이 중간에 죽어도 그때까지 쓴 줄은 살아남아요. 파일을 통째로 열지 않아도 `grep`으로 셀 수 있다. 지연 필드는 "느리다"는 체감을 "어느 구간이 느리다"로 바꿔 주는 유일한 값.

2. `run_eval`: 반환 스키마를 그대로 지킬 것.

   ```python
   {
     "total": 14,
     "passed": 11,
     "by_type": {"fact": {"total": 5, "passed": 5}, "no_answer": {...}},
     "failures": [{"id": "d5-01", "type": "guardrail", "status": "fail", "detail": "..."}],
   }
   ```

   통과 여부는 `judge`가 주어지면 그 함수가 정하고, 없으면 답이 비어 있지 않은지만 보면 됩니다. 판정을 바깥에서 갈아 끼울 수 있어야 같은 평가셋으로 기준을 바꿔 가며 재 볼 수 있으니까요.

   그리고 한 문항이 예외를 던져도 전체가 멈추면 안 됩니다. 그 문항은 `status`를 `error`로 남기고 다음으로 넘어갈 것. 14문항 돌리다 3번째에서 죽으면 나머지 11문항의 상태를 영영 모른다. 평가 한 판에 드는 건 시간과 토큰인데, 그걸 다 태우고도 결과가 없으면 다음부터는 측정을 건너뛰게 됩니다. 틀린 답과 터진 코드를 굳이 나눠 적는 이유도 같다. 고칠 사람도 고칠 자리도 다르니까.

   `failures`에는 문항 id를 반드시 남길 것. 심화의 `compare_eval`이 그 목록으로 전후를 비교하기 때문입니다.

3. `eval_set.json`: Day2부터 누적해 12문항 이상, 5유형 이상. `fact`와 `no_answer`는 반드시 들어 있어야 하고, id는 저장소 전체에서 중복되면 안 됩니다.

   왜 다섯 유형일까요? 평균 하나로 품질을 말하지 못하게 하려는 것. `fact`만 스무 개 담긴 평가셋은 통과율 95%를 쉽게 만듭니다. 가드레일이 통째로 뚫려 있어도 그 숫자는 그대로 95%.

4. `day07/growth.md`: Day2에 심어 둔 문항 중 그때 실패했던 것을 회수합니다. 지금은 통과하는지, 무엇이 그걸 바꿨는지를 100자 이상 쓰고 문항 id를 함께 적을 것.

   여기가 오늘의 본론이에요. "전보다 나아졌다"와 "`d2-03`은 Day2에 없는 사실을 지어냈고 지금은 거절한다, 바꾼 건 검색 게이트다"는 전혀 다른 문장. 앞의 것은 6일치 작업을 하나도 증명하지 못합니다. 뒤의 것은 다음에 무엇을 건드리면 안 되는지까지 알려 준다.

### 채점 기준 (기초 7점)

| 배점 | 항목 | 판정 기준 |
|---|---|---|
| 2점 | **평가셋 누적** | 12문항 이상, 5유형 이상, `fact`·`no_answer` 포함, id 중복 없음 |
| 2점 | **집계 형식** | 반환 스키마 준수, 유형별 합이 전체와 일치 |
| 1점 | **예외 격리** | 한 문항이 터져도 전체가 멈추지 않고 그 문항이 `error`로 기록됨 |
| 1점 | **계측** | 이벤트 기록 + 지연 필드 + JSON Lines dump |
| 1점 | **확장 검사 게이트** | 10개 중 8개 이상 (`growth.md` 포함) |

확장 검사 공개분은 여섯 개. 빈 평가셋에서 `total`이 0 / 주입한 `judge`가 전부 불통과로 판정하면 `passed`도 0 / 전부 통과로 판정하면 그대로 반영 / `failures`의 모든 항목에 `id` 존재 / `growth.md` 존재 / 그 내용이 100자 이상. 다섯 개를 못 넘기면 그 자리에서 실패고 나머지 넷은 채점 때 붙는 몫.

## 심화 파트 (3점)

### 왜 필요한가

통과율 총합만 보면 어느 유형이 좋아졌고 어느 유형이 깨졌는지 알 수 없다. 한 유형을 고치다 다른 유형을 깨뜨리는 일은 자주 생깁니다. 근거를 더 길게 인용하라고 프롬프트를 한 줄 고쳤더니 `fact`가 오르고 `no_answer`가 무너지는 식으로. 전체 점수가 2점 올랐다면 배포해도 될까요? 그 안에서 안전 유형이 뚫렸다면 안 됩니다. 그 사실이 드러나는 곳은 문항 단위 비교뿐.

### 구현할 것

```python
compare_eval(before, after) -> {"fixed": [...], "regressed": [...], "delta": int, "safe": bool}
```

- `fixed`: before에서 실패했다가 after에서 통과한 문항 id
- `regressed`: before에서 통과했다가 after에서 실패한 문항 id
- `delta`: after의 통과 수에서 before의 통과 수를 뺀 값
- `safe`: `regressed`가 비었으면 `True`

`safe`를 언제나 `False`로 두면 회귀 탐지는 통과하고 회귀 없음 판정에서 떨어집니다. 채점기가 그 경우를 따로 보는 이유가 있죠. 늘 위험하다고 말하는 게이트는 두어 달이면 아무도 읽지 않습니다. 진짜 회귀가 났을 때도 같은 경고에 묻혀 지나간다. 과탐지가 미탐지보다 안전해 보여도 운영에서 도착하는 곳은 결국 같은 자리.

### 채점 기준 (심화 3점)

| 배점 | 항목 | 판정 기준 |
|---|---|---|
| 1점 | **비교의 결정성** | 개선과 회귀를 정확히 분리 |
| 1점 | **회귀 탐지** | 통과 수가 늘어도 회귀가 있으면 `safe=False` |
| 1점 | **회귀 없음 판정** | 무조건 `False`를 내는 구현은 인정하지 않음 |
