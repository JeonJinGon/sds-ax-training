# Day 2. 런북 RAG와 평가셋

[← 전체 미션 맵](../README.md)  ·  [← Day 1](../day01/README.md)  ·  [Day 3 →](../day03/README.md)

어제 만든 트리아지가 `payment-api` 알람을 P1으로 올린 지 3분. 대응 채널에 올라온 질문 하나. "지금 롤백해도 되나요?"

사내 런북을 물린 RAG의 대답. "온콜은 주 단위로 순환하며 매주 월요일 오전 10시에 인수인계합니다."

틀린 문장은 아니에요. 다만 물어본 것과 아무 상관이 없을 뿐. 여기서 대부분 프롬프트를 열고 "반드시 근거 문서만 보고 답하라"를 덧붙입니다. 열 번을 고쳐도 답은 그대로. 모델이 받아 본 문서에 롤백 기준이 처음부터 없었으니까요. 검색이 `oncall_policy.md`를 물어 온 순간에 승부는 끝난 겁니다.

## 학습 목표

- 메타데이터를 청킹 전에 붙여야 상속된다는 것. 순서를 바꿔 보면 바로 보입니다.
- 검색 결과를 프롬프트에 실제로 주입하기. 어느 문서를 근거로 썼는지 함께 돌려주는 것까지.
- 답이 틀렸을 때 검색 단계부터 의심하는 법. (심화)
- 과정 전체를 관통할 `eval_set.json`을 여기서 시작하기.

## 기초 파트 (7점)

### 구현할 것

```python
build_chunks(doc_paths)             # 문서 경로 목록 -> Document 리스트
build_retriever(vectorstore)        # 벡터저장소 -> retriever
build_rag_chain(retriever, llm=None)  # 질문 -> {"answer": str, "sources": [...]}
```

### 요구사항

1. `build_chunks`: 모든 청크의 `metadata`에 세 키를 넣을 것. `source`는 원본 파일명, `department`는 담당 조직, `updated_at`은 최종 수정일 (`YYYY-MM-DD`).

   답이 이상할 때 어디부터 되짚는가? 결국 이 세 키입니다. 어느 파일에서 나왔는지 모르면 고칠 문장부터 못 찾고 `department`가 없으면 "이 답 이상한데요"를 누구에게 보낼지 정할 수 없습니다. `updated_at`은 반년 전에 폐기된 런북을 근거로 든 답을 걸러내는 유일한 단서.

   메타데이터는 청킹 **전에** 붙일 것. 순서를 틀리면 상속이 안 되는데 오류도 나지 않아서 한참 뒤 운영에서 출처가 빈 답을 보고서야 알아챕니다. 분할에는 `RecursiveCharacterTextSplitter`나 `MarkdownHeaderTextSplitter`를 씁니다. 실습 문서는 740~921자니까 `chunk_size`는 800 이하로. 그보다 크면 통째로 한 청크가 되는 문서가 생겨요.

2. `build_retriever`: `vectorstore.as_retriever(...)`로 만들고 `k`를 명시합니다.

   숫자 하나로 정확도와 비용이 같이 정해지는 자리. `k`가 너무 작으면 정답 청크를 아예 못 가져오고 너무 크면 무관한 런북이 컨텍스트를 채워 모델이 그쪽으로 끌려가죠. 왜 그 값을 골랐는지 주석 한 줄을 남겨 두면 다음에 튜닝할 때 기준이 생깁니다.

3. `build_rag_chain`: 질문 문자열을 받아 아래 형태를 반환합니다.

   ```python
   {"answer": "연차는 최대 5일까지 이월됩니다.", "sources": ["leave_policy.md"]}
   ```

   `sources`에는 실제로 검색된 문서에서 뽑은 값을 넣습니다. 지어낸 파일명이 들어가면 안 돼요.

   출처가 없는 답은 운영에서 근거가 못 된다. 담당자가 원문을 열어 한 줄 확인한 다음에야 조치가 나가니까요. 없는 파일명을 적어 보내는 쪽은 더 나쁘죠. 확인하러 간 사람의 5분과 그 시스템에 대한 신뢰를 같이 태우는 셈.

4. `eval_set.json` (저장소 루트): 5문항 이상을 쓰되 아래 세 유형을 모두 포함할 것.

   ```json
   [
     {"id": "d2-01", "question": "연차는 며칠까지 이월되나요?",
      "type": "fact", "expected_source": "leave_policy.md"},
     {"id": "d2-02", "question": "남은 휴가를 내년에 쓸 수 있나요?",
      "type": "paraphrase", "expected_source": "leave_policy.md"},
     {"id": "d2-03", "question": "사내 헬스장 운영 시간은?",
      "type": "no_answer", "expected_source": null}
   ]
   ```

   `fact`는 문서에 그대로 적힌 것을 묻는 질문, `paraphrase`는 같은 내용을 다른 말로 물어 검색이 진짜 되는지 보는 질문. `no_answer`는 문서에 아예 없는 것. 모른다고 답해야 정답이다.

   id는 `d{Day번호}-{일련번호}` 형식 (예: `d2-01`). Day3 이후 추가분은 `d3-`, `d4-`로 이어 붙이고 저장소 전체에서 중복되면 안 됩니다.

   평가셋이 없으면 프롬프트를 고친 뒤에 좋아졌는지 나빠졌는지 말할 방법이 없고, 세 유형을 굳이 나눠 놓는 이유도 같습니다. `paraphrase`가 없으면 단어가 겹쳐서 맞힌 건지 검색이 된 건지 구분이 안 되고 `no_answer`가 없으면 "모른다고 답하는 능력"은 아무도 측정하지 않은 채로 배포됩니다.

### 채점 기준 (기초 7점)

| 배점 | 항목 | 확인 방법 |
|---|---|---|
| 2점 | **메타데이터 상속** | 모든 청크에 세 키가 존재. 청킹 전에 붙였는지를 봅니다 |
| 1점 | **청킹 전략** | 청크 수가 합리적 범위이고 원문이 보존됨. 단순 고정 길이 자르기가 아님 |
| 2점 | **컨텍스트 주입** | 검색된 문서 본문이 모델에게 보낸 프롬프트에 실제로 들어 있음 |
| 1점 | **출처 반환** | `sources`가 실제 검색 결과와 일치. 지어낸 값이 아님 |
| 1점 | **확장 검사 게이트** | 10개 중 8개 이상 |

로컬에서 도는 공개분은 여섯 개, 다섯 개 이상 통과해야 하고, 평가셋 형식 세 가지와 빈 질문·아주 긴 질문·특수문자 질문이 거기 들어 있어요. 운영 채널에 올라오는 질문은 생각보다 지저분하니까요.

## 심화 파트 (3점)

### 왜 필요한가

RAG가 틀린 답을 내면 손이 먼저 프롬프트로 갑니다. 그런데 정작 검색이 정답 청크를 못 가져온 상황이라면? 모델을 바꿔도 소용없습니다. 답을 만들기 전에 검색 결과부터 보고 쓸 만하지 않으면 모른다고 답할 것.

### 구현할 것

```python
assess_retrieval(docs, question) -> dict
```

그리고 `build_rag_chain`이 이 판정을 거쳐 동작하도록 연결합니다.

### 요구사항

1. 검색 품질 판정: `assess_retrieval`은 **LLM을 호출하지 않고** 검색 결과가 쓸 만한지 판정할 것.

   ```python
   {"usable": True, "reason": "질의어 3개 중 2개가 본문에 등장", "matched": 2}
   ```

   판정 근거는 자유롭게 잡을 것. 질문에서 핵심어를 뽑아 본문에 몇 개나 등장하는지 세도 되고 문서 개수나 길이를 봐도 됩니다. 조건은 하나. 결정적이어야 하고 같은 입력에는 항상 같은 출력이 나와야 합니다. 게이트마저 LLM에게 맡기면 무엇이 틀렸는지 영원히 못 잡는 구조.

2. 검색 결과가 없거나 쓸모없으면 거절: `usable`이 `False`면 모델에게 묻지 말고 바로 거절 응답을 만들 것.

   ```python
   {"answer": "제공된 문서에서 답을 찾을 수 없습니다.", "sources": []}
   ```

   거절 응답에는 `찾을 수 없` 문구가 들어가야 하고 `sources`는 빈 목록으로 둘 것.

   모델을 부르기 전에 끊는 게 핵심. 근거를 안 주고 물어도 모델은 어떻게든 답을 만들어 내는데, 장애 대응 중에 잘못된 롤백 기준을 받아 든 사람에게는 그걸 검증할 시간이 없습니다. 모른다는 답이 그럴듯한 오답보다 싸게 먹히는 자리.

3. 연결: 문서와 무관한 질문을 넣었을 때 체인이 사실을 지어내지 않을 것.

### 채점 기준 (심화 3점)

| 배점 | 항목 | 확인 방법 |
|---|---|---|
| 1점 | **판정의 결정성** | 관련 문서 / 무관 문서 / 빈 목록에서 각각 다르게 판정. 상수 반환이면 실패 |
| 1점 | **거절 경로** | 검색 결과가 비었을 때 모델을 호출하지 않고 거절. `sources`가 빈 목록 |
| 1점 | **파이프라인 연결** | 무관한 질문에서 모델이 그럴듯한 답을 줘도 체인이 그 답을 거절로 바꿈 |
